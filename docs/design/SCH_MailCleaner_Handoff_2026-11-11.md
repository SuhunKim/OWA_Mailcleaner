## 1. 요청받은 결함 4건과 처리 상태

| # | 요청 | 구현 | 실제 동작 확인 |
|---|---|---|---|
| 1 | 휴지통 이동을 메일별로 검증 | 완료(소스) | **미확인** — 사용자가 아직 시험하지 않음 |
| 2 | 읽음 처리를 최종 상태로 검증 | 완료(소스) | 상태 표시는 사용자 확인. **읽음 처리 실행 결과는 미확인** |
| 3 | 예외·중단 시 결과 정확히 집계 | 완료(소스) | **미확인** |

## 2. 한 것

### 2.1 결과 집계 (요청 3)
- 건별 결과 6종: 반영 확인 / 이미 처리됨 / 건너뜀 / 실패(요청 전 오류, 처리 후 미반영) / 결과 미확인(요청이 갔을 수 있음) / 미처리(요청 전 중단). 선택 건수 = 6종 합계이며 다르면 "집계 불일치"를 표시한다.
- 요청 클릭 직전에 `sent` 표시를 올리고, 클릭 전에 발생한 페이지 스크립트 오류(`SiteScriptError`)만 "요청 안 보냄"으로 본다. 그 외 오류는 모두 "요청이 갔을 수 있음"으로 취급한다.
- 결과가 불명확하면 이후 그룹 요청을 중단하고 자동 재시도하지 않는다. 결과 문구에 사유별 건수와 수락/비수락 확인창 내용을 표시한다.
- 상태 색상은 결과 수준(ok/warn/error)을 명시해 정한다. 문구에 "실패 0건"이 있어 항상 붉게 나오던 문제를 고쳤다.

### 2.2 읽음 처리 (요청 2)
- 안 읽음 판정: 행 클래스 `td_list_bold` = 안 읽음, 클래스 없음 = 읽음, 그 외 값 = 판별 불가. 근거: 2026-11-11 받은 편지함에서 `td_list_bold` 270건 + 빈 클래스 106건 = 376건이며 사이트 메뉴의 안 읽음 숫자 270과 일치. 이 매핑은 이 한 폴더·한 시점에서 검증했다. 다른 폴더·다른 클래스 값은 미검증.
- 이미 읽음 표시된 메일은 요청을 보내지 않고 "이미 처리됨"으로 집계한다.
- 성공 판정: 요청 후 최종 목록의 해당 메일 상태가 읽음일 때만 반영 확인. 요청 시 사이트 문서에 표식(`data-sch-mc`)을 달아 화면 갱신 여부를 구분한다. 갱신 후에도 안 읽음이면 "처리 후 미반영", 갱신을 확인하지 못했으면 "결과 미확인".
- 상태 아이콘(`/img/wma/status/*.GIF`)의 의미는 확정하지 못했다. 파일명은 `Icon`으로 수집만 하며 판정에는 쓰지 않는다. 확인된 값: 읽음 행 대부분 `R2A.GIF`, 일부 `R2AF.GIF`. 안 읽음 행의 아이콘은 아직 분포를 보지 못했다.

### 2.3 휴지통 이동 (요청 1)
- 실행 전 지운 편지함 전체를 기록 → 그룹마다 사이트 총 건수가 정확히 그 그룹만큼 줄었는지 확인(다음 요청의 게이트) → 마지막에 원본 폴더·지운 편지함을 전체 재조회해 메일별로 판정.
- 반영 확인 조건: 원본에서 사라짐 **그리고** 지운 편지함에 같은 `data-mid`·보낸이·제목·수신시각·크기의 메일이 새로 나타남. 원본에서 사라졌으나 도착을 확정 못 하면 "결과 미확인".
- 폴더 이동 후 사이트가 `data-mid`를 유지하는지에 대한 기존 근거는 없었다(문서·README 검색 결과 없음). 실제 시험에서 유지되지 않으면 이동은 대부분 "결과 미확인"으로 나온다. 이 결과 자체가 근거가 된다.
- 메일 식별 변경: 기존 `mail_list-N`(행 id)은 목록 순번이라 메일 삭제·신규 수신 시 밀린다. 이제 `ReadMailbox.js`가 체크박스의 `data-mid`를 `Id`로 반환하고 모든 대조는 이것으로 한다. 행 선택도 `data-mid` 기준이다.

### 2.4 실행 중 제한 (요청 4)
- 실행(검색 포함) 중 사이트 보기·로그인 창 열기·개발자 도구·화면 구조 복사 버튼 비활성, 로그인 창 숨김·입력 차단, 기본 확인창 비활성(실행 종료 후 복원).
- 사이트 확인창은 요청 단위로 기대값(종류·문구 패턴·표시 건수)과 일치할 때만 수락한다. 불일치는 수락하지 않고 기록하며 이후 요청을 중단한다.
- 문구 패턴은 **실제 사이트 문구를 확인하지 못한 가정**이다: 읽음 `읽`, 이동 `삭제|지운\s*편지함|휴지통|이동`, 비우기 `비우|영구|삭제|지운\s*편지함`. 확인창이 수락되지 않아 중단되면 결과 문구에 표시된 실제 문구로 패턴을 고친다.
- 클릭과 계정·폴더·선택 상태 검증은 한 번의 페이지 스크립트로 수행한다(그 사이 변경 불가).
- 지운 편지함 비우기: 앱 확인창에 계정·폴더·건수 표시 → 클릭과 같은 스크립트에서 세 값 재검증 → 실행 후 같은 계정의 지운 편지함이 0건인지 확인. 일부만 줄었거나 변화 없으면 "결과 미확인"(재시도 없음).

### 2.5 사용자 요청으로 추가·변경한 UI
- "안 읽은 메일만" 체크박스(기본 해제). 체크하면 안 읽음 메일만 목록에 담는다.
- 체크하지 않으면 조건에 맞는 모든 메일(읽은 것 포함)을 목록에 보여 준다. 읽음 처리 모드에서는 안 읽음만 처음에 체크, 휴지통 이동 모드는 기존처럼 전부 체크. 읽은 메일을 직접 체크해 실행해도 요청은 보내지 않고 "이미 처리됨"으로 집계.
- 검색 결과에 읽음 상태 판별 불가 건수와 진단 문구(아이콘·행 클래스·건수 분포)를 표시한다. 판별 불가가 있을 때만 나온다.

## 3. 사용자가 확인한 것
- 상태 열에 읽음/안 읽음이 표시된다. 읽은 메일은 목록에 보이고 기본 체크가 해제되어 있다.
- 이전 세션에서 읽음 처리가 실제로 동작함을 확인했다(옛 UI·옛 판정 방식).

## 4. 안 한 것 / 미검증
1. 읽음 처리 실행 시험: 안 읽은 메일 1~2건 → "반영 확인", 지연·중단 없는지. (이전 빌드에서는 상태 판별이 안 되어 25초 대기 후 "결과 미확인" 중단이 났다. 판별 수정 후 재시험 전.)
2. 읽은 메일을 체크해 실행했을 때 "이미 처리됨" 집계.
3. 휴지통 이동 전체(메일별 판정, `data-mid` 유지 여부, 게이트, 중단 동작).
4. 지운 편지함 비우기와 확인창 문구 패턴.
5. 읽음 처리 중 중단 버튼, 사이트 세션 만료, 계정 변경 시의 집계.
6. 다른 폴더(내게 쓴 편지함·보낸 편지함)에서의 상태 판정(`td_list_bold` 규칙).
7. 첨부만 삭제: 미구현·미확인(메일 상세 화면 구조 필요). 작업지시서 3단계 그대로.
8. 안 읽음/첨부 아이콘 해석(`첨부` 열은 계속 `-`).
9. 배포: `publish\SchMailCleaner.exe`는 **이전 빌드**이며 이번 수정이 없다. `build.ps1`로 다시 만들어 사용자 확인 후에만 배포 완료로 본다.

## 5. 다음 작업 순서
1. 사용자가 새 빌드로 읽음 처리 1~2건 시험 → 결과 문구 수집 → 실패 시 해당 문구로 수정.
2. 읽음 처리 확인 후 테스트 메일 1건으로 휴지통 이동 시험(사용자 수행). 결과 문구로 ID 유지 여부 확정, 미유지면 "도착 확인" 방식을 재설계(예: 지운 편지함 조회 기준) 하거나 미확인 표시를 유지하고 한계를 README에 기록.
3. 확인창 실제 문구를 기록하고 패턴을 확정.
4. 지운 편지함 비우기는 사용자가 직접 시험(되돌릴 수 없음).
5. 시험 결과 반영 후 `build.ps1`로 배포본 재생성, README·ADMIN_GUIDE의 미구현/미검증 표 갱신.

## 6. 작업 방법 메모
- 이번 세션의 빌드는 `dotnet build -c Debug -o <임시폴더>`로 했고 `SchMailCleaner\obj\`가 생성·갱신됐다(소스 아님). 실행한 디버그 EXE는 임시 폴더에 있으며 프로젝트의 `publish\`에는 반영되지 않았다.
- 앱 화면 문구(검색 결과·실행 결과)는 Windows UI Automation으로 읽을 수 있어 사용자가 문구를 복사하지 않아도 확인할 수 있다. 사용자가 클립보드에 캡처한 이미지도 읽을 수 있다. 메일 제목·본문·계정 정보를 문서에 옮기지 않는다.
- `Ctrl+Shift+D`(화면 구조 복사)는 메일 제목·발신자를 일부 포함한 행 구조를 복사하므로, 결과 문서에는 옮기지 않았다.
- 진단용 상태 분포 문구는 상태 판별이 안정화되면 제거해도 된다(`SearchAsync`의 `[진단]`).
